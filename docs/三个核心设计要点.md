## 一、商品 / SKU 分离

### 真实数据：华为 P20（product_id = 26）

**`pms_product`（商品主表，展示单位）**

| id | name | price | stock | sale | product_sn |
|---|---|---|---|---|---|
| 26 | 华为 HUAWEI P20 | 3788.00 | **1000** | 100 | 6946605 |

**`pms_sku_stock`（SKU 表，库存单位）**

| id | sku_code | price | stock | lock_stock | sp_data |
|---|---|---|---|---|---|
| 110 | 201806070026001 | 3788.00 | 487 | 0 | `[{"key":"颜色","value":"金色"},{"key":"容量","value":"16G"}]` |
| 111 | 201806070026002 | **3999.00** | 499 | 0 | `[{"key":"颜色","value":"金色"},{"key":"容量","value":"32G"}]` |
| 112 | 201806070026003 | 3788.00 | 500 | 0 | `[{"key":"颜色","value":"银色"},{"key":"容量","value":"16G"}]` |
| 113 | 201806070026004 | **3999.00** | 500 | 0 | `[{"key":"颜色","value":"银色"},{"key":"容量","value":"32G"}]` |

### 四个要点

**1. 价格必须挂在 SKU 上，不能挂在商品上**

同一个商品，16G 卖 3788、32G 卖 3999。如果价格只存在于 `pms_product`，就没法支持"同商品不同规格不同价"。

**2. 库存的权威来源是 SKU，不是商品**

⚠️ **注意一个数据不一致**：
```
4 个 SKU 库存合计 = 487 + 499 + 500 + 500 = 1986
pms_product.stock                       = 1000   ← 对不上
```
`pms_product.stock` 是一个**冗余的汇总展示字段**，和 SKU 库存不同步（种子数据没维护好）。
**结论：判断真实库存必须查 `pms_sku_stock.stock`，`pms_product.stock` 不可信。**

> 这是个很实用的习惯：**看到冗余字段，一定要先确认哪一个是权威来源。**

**3. `sp_data` 用 JSON 存销售属性，而不是关联表**

```json
[{"key":"颜色","value":"金色"},{"key":"容量","value":"16G"}]
```
为什么不用关联表？因为不同商品的**属性维度是动态的**——手机有颜色/容量，衣服有尺码/颜色，书可能只有版本。用 JSON 可以灵活扩展，代价是**无法用 SQL 直接按属性过滤**（这也是为什么搜索要靠 Elasticsearch）。

**4. `lock_stock`（锁定库存）是防超卖的抓手**

当前都是 0，因为没有待支付订单占着库存。设计意图是两阶段扣减：
```
下单 → stock - n，lock_stock + n     （先锁住，不真扣）
支付 → lock_stock - n               （真扣完成）
超时未支付 → stock + n，lock_stock - n  （释放回滚）
```

|---|---|

| 36 | 8 |
| 35 | 8 |

## 二、订单做快照

### 证据 A：同一订单里，同一商品有两个价格 ★

```sql
SELECT oi.order_id, oi.product_id, oi.product_name AS snapshot_name,
       p.name AS current_name, oi.product_price AS snap_price, p.price AS now_price
FROM oms_order_item oi LEFT JOIN pms_product p ON oi.product_id = p.id;
```

| order_id | product_id | 快照名 | 现名 | 快照价 | 现价 |
|---|---|---|---|---|---|
| 12 | 26 | 华为 HUAWEI P20 | 华为 HUAWEI P20 | 3788.00 | 3788.00 |
| **12** | **28** | **红米5A** | 小米 红米5A 全网通版 3GB+32GB... | **649.00** | 649.00 |
| **12** | **28** | **红米5A** | 小米 红米5A 全网通版 3GB+32GB... | **699.00** | 649.00 |
| 12 | 29 | Apple iPhone 8 Plus | Apple iPhone 8 Plus 64GB... | 5499.00 | 5499.00 |

**同一个订单里，`product_id = 28` 出现了两次，快照价一个 649、一个 699，而商品现价是 649。**

这只能有一个解释：**下单那一刻的价格被冻结了**。用户当时确实按 699 成交过，商品后来降价，但历史订单不能被改写。

### 证据 B：商品改名了，订单里还是旧名

对比 `snapshot_name` 和 `current_name`：

| 快照名（下单时） | 现名（运营改过） |
|---|---|
| 小米8 | 小米8 全面屏游戏智能手机 6GB+64GB 黑色 全网通4G 双卡双待 |
| 红米5A | 小米 红米5A 全网通版 3GB+32GB 香槟金 移动联通电信4G手机 双卡双待 |

商品名被改成了带详细参数的营销版本，但订单里保存的是下单时的短名。

**这是必须的**：如果订单靠 JOIN 商品表取名称，那每次商品改名，所有历史订单的"买了什么"都会跟着变——**交易凭证就失真了**。

### 证据 C：收货地址也必须快照

| id | member_id | receiver_name | receiver_city | receiver_detail_address |
|---|---|---|---|---|
| 12 | 1 | 大梨 | **常州市** | 东晓街道 |
| 13 | 1 | 大梨 | **深圳市** | 东晓街道 |
| 14 | 1 | 大梨 | **深圳市** | 东晓街道 |

**同一个会员（member_id = 1）的订单，收货城市不一样**（常州市 / 深圳市）。

`oms_order` 里存了完整的 `receiver_name` / `receiver_phone` / `receiver_province` / `receiver_city` / `receiver_region` / `receiver_detail_address`，**完全不关联 `ums_member_receive_address`**。

理由：用户改一次收货地址，绝不能把所有历史订单的收货地址都改掉——那是历史事实。

### 冗余快照的完整清单

`oms_order_item` 从商品表复制了这些字段：

```
product_name        商品名称
product_pic         商品主图
product_sn          货号
product_brand       品牌名      ← 报表按品牌统计销量也要还原历史
product_price       成交价
product_category_id 分类 id     ← 同上
product_attr        销售属性（JSON）
```

`oms_cart_item` 也做了同样的事（`product_name` / `product_pic` / `product_sub_title` / `product_brand` / `product_sn`），但目的不同——**购物车冗余是为了渲染速度，订单冗余是为了历史准确**。

> **一句话总结**：购物车的冗余是性能优化，订单的冗余是业务正确性。

## 三、权限动态化

### 完整链路

```
① ums_resource 表（31 条）
   存 url（Ant 风格路径）
        ↓ 启动时
② MallSecurityConfig.dynamicSecurityService().loadDataSource()
   读全表，构建 Map<url, "id:name">
        ↓ @PostConstruct
③ DynamicSecurityMetadataSource
   缓存 Map；每个请求用 AntPathMatcher 匹配出所需权限
        ↓
④ DynamicAuthorizationManager.check()
   所需权限 ∩ 用户已有权限 ≠ ∅ → 放行
        ↓
⑤ clearDataSource() 清缓存
   改完资源后调用 → 下次请求惰性重载，无需重启
```

### 代码细节

**① 权限的"身份"是个字符串**

```java
// mall-admin/src/main/java/com/macro/mall/config/MallSecurityConfig.java
@Bean
public DynamicSecurityService dynamicSecurityService() {
    return new DynamicSecurityService() {
        @Override
        public Map<String, ConfigAttribute> loadDataSource() {
            Map<String, ConfigAttribute> map = new ConcurrentHashMap<>();
            List<UmsResource> resourceList = resourceService.listAll();
            for (UmsResource resource : resourceList) {
                map.put(resource.getUrl(),
                        new SecurityConfig(resource.getId() + ":" + resource.getName()));
            }
            return map;
        }
    };
}
```

value 是 `"5:商品管理"` 这样的字符串。用户登录时查出的权限也是同一格式，所以后面能用 `contains` 直接比对——**权限的比对变成了字符串比对**。

**② URL 匹配用 AntPathMatcher**

真实的 `ums_resource.url` 数据（共 31 条）：

| id | name | url |
|---|---|---|
| 1 | 商品品牌管理 | `/brand/**` |
| 3 | 商品属性管理 | `/productAttribute/**` |
| 5 | 商品管理 | `/product/**` |
| 6 | 商品库存管理 | `/sku/**` |
| 8 | 订单管理 | `/order/**` |
| 9 | 订单退货申请管理 | `/returnApply/**` |
| 13 | 优惠券管理 | `/coupon/**` |
| 15 | 限时购活动管理 | `/flash/**` |

按分类分布：商品 6 条 / 订单 5 条 / 营销 10 条 / 用户 7 条 / 其他 3 条。

`/product/**` 能同时匹配 `/product/list`、`/product/update/1`、`/product/create`。

**③ 鉴权是"取交集"，命中一条就放行**

```java
// mall-security/src/main/java/com/macro/mall/security/component/DynamicAuthorizationManager.java
List<ConfigAttribute> configAttributeList = securityDataSource.getConfigAttributesWithPath(path);
List<String> needAuthorities = configAttributeList.stream()
        .map(ConfigAttribute::getAttribute).collect(Collectors.toList());

Collection<? extends GrantedAuthority> grantedAuthorities = currentAuth.getAuthorities();
List<? extends GrantedAuthority> hasAuth = grantedAuthorities.stream()
        .filter(item -> needAuthorities.contains(item.getAuthority()))
        .collect(Collectors.toList());

if (CollUtil.isNotEmpty(hasAuth)) {
    return new AuthorizationDecision(true);   // 命中任意一条即放行
} else {
    return new AuthorizationDecision(false);
}
```

⚠️ **语义注意**：是"**或**"不是"**且**"——所需权限里有任意一条命中就放行。如果一条路径匹配到多个规则，权限要求反而更宽松。

前面的处理顺序：
1. 白名单（`secure.ignored.urls`）→ 直接放行
2. `OPTIONS` 预检请求 → 直接放行（CORS）
3. 才走上面的权限校验

**④ 免重启刷新的实现：置 null + 惰性重载**

```java
// DynamicSecurityMetadataSource
private static Map<String, ConfigAttribute> configAttributeMap = null;

@PostConstruct
public void loadDataSource() {
    configAttributeMap = dynamicSecurityService.loadDataSource();
}

public void clearDataSource() {
    configAttributeMap.clear();
    configAttributeMap = null;          // ← 置 null
}

@Override
public Collection<ConfigAttribute> getAttributes(Object o) {
    String path = URLUtil.getPath(((FilterInvocation) o).getRequestUrl());
    return getConfigAttributesWithPath(path);
}

public List<ConfigAttribute> getConfigAttributesWithPath(String path) {
    if (configAttributeMap == null) this.loadDataSource();   // ← 惰性重载
    ...
}
```

`UmsResourceController` 注入了 `DynamicSecurityMetadataSource`，在增删改资源后调 `clearDataSource()`。置 null 之后，**下一个请求会触发重新读表**——这就是"改权限不用改代码、不用重启"的实现方式。

**⑤ 一个日志里能验证的细节**

启动时日志显示：`select ... from ums_resource` → **Total: 31**（加载全部资源构建 Map）
登录后日志显示：`getResourceList`（adminId=1）→ **Total: 29**

**31 是全部资源，29 是 `test` 用户实际被授予的**。差的 2 条就是他被剥夺的权限。

### 可以优化的点（面试可讲）

`getConfigAttributesWithPath()` 每次请求都要**遍历整个 Map**，对每条规则跑一次 `AntPathMatcher.match()`：

```java
Iterator<String> iterator = configAttributeMap.keySet().iterator();
while (iterator.hasNext()) {
    String pattern = iterator.next();
    if (pathMatcher.match(pattern, path)) {
        configAttributes.add(configAttributeMap.get(pattern));
    }
}
```

31 条规则时开销可忽略，但**规则上千条时会成为性能热点**（每个请求 O(n) 次正则级匹配）。

优化方向：
- 按 URL 第一段建索引（`/product/**` 归到 `product` 桶），先按首段过滤
- 或给"路径 → 所需权限"加一层 Caffeine 本地缓存（命中率极高，因为接口路径是有限的）
- 或改用前缀树（Trie）做路径匹配

> **面试话术**：这个设计的好处是**权限与代码解耦**、改权限免重启；代价是**每次请求要遍历规则做路径匹配**。在 mall 的规模下完全可接受，但如果权限规则数量级上来，需要加缓存或建索引。

## 三个设计的共同主题

| 设计 | 解决的问题 | 核心手法 |
|---|---|---|
| 商品 / SKU 分离 | 同商品不同规格的价格与库存 | **拆成两层**：展示单位 vs 库存单位 |
| 订单做快照 | 商品会变，但历史订单不能变 | **冗余存副本**：冻结交易那一刻 |
| 权限动态化 | 权限规则不能写死在代码里 | **外置 + 缓存 + 惰性重载** |

这三个都能在面试里讲，而且属于"**能说出为什么**"的层次，不是背概念。
