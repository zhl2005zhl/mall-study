## 一、先给判断依据

判断"某段代码值不值得读源码"，看三个条件：

| 条件 | 说明 |
|---|---|
| **有实现技巧** | 不是照着需求直译的样板代码 |
| **有取舍** | 存在多个可选方案，作者选了其中一个 |
| **有反常识处** | 读之前猜不到，读之后"原来如此" |

按这三条筛：

| 设计 | 设计含量 | 在读代码？ | 结论 |
|---|---|---|---|
| 权限动态化 | **高** | ✅ 在代码里 | **必读** |
| 商品 / SKU 分离 | 高 | ❌ 在表结构里 | 读表 + 读 2 段 |
| 订单做快照 | 高 | ❌ 在业务约定里 | 只读 3 段 |

**注意**：后两个"设计含量高"，但含量体现在**数据库设计和业务约定**上，代码只是忠实地执行（`setXxx` 复制字段）。读代码学不到东西，读设计意图才有收获。

### 为什么这段值得精读

**① 它是"框架扩展"的范例**，不是"用框架"。面试时"我会用 Spring Security"和"我给 Spring Security 做了动态权限扩展"是两个层次。

**② 代码量小但完整**，25 KB 里包含了：接口抽象、策略模式、缓存 + 惰性失效、过滤器链定制、JWT 手写实现。密度极高。

**③ 有反常识的设计**（`DynamicAuthorizationManager.java`）：

```java
if (CollUtil.isNotEmpty(hasAuth)) {
    return new AuthorizationDecision(true);   // 命中任意一条即放行

```

这是 **"或"不是"且"**。如果一条路径匹配到多个权限规则，**权限要求反而更宽松**。读之前不容易猜到。

**④ 有明确的代价**（面试加分点）：

`getConfigAttributesWithPath()` 每个请求都要遍历整个 Map，对每条规则跑一次 `AntPathMatcher.match()`。31 条规则时可忽略，规则上千条会成为热点（每请求 O(n) 次路径匹配）。

### 代码里唯一值得读的 2 处

#### ① `realStock` 的计算 —— 真实可用库存

```
mall-portal\src\main\java\com\macro\mall\portal\service\impl\OmsPromotionServiceImpl.java:53
```

`realStock = stock - lockStock`，这才是**用户看到的可卖库存**。

> **顺手可做的改造**：这行代码在同一个文件里**重复了 4 次**（第 53、73、96、167 行）。可以提取成 `PmsSkuStock` 的领域方法 `getRealStock()`，或做成数据库计算列 / 视图。属于"低风险、能说清动机"的重构，适合作为简历上的小改造。

#### ② `lockStock` —— 下单锁库存 ★★ 这段有并发缺陷

```
mall-portal\src\main\java\com\macro\mall\portal\service\impl\OmsPortalOrderServiceImpl.java:734-740
```

```java
private void lockStock(List<CartPromotionItem> cartPromotionItemList) {
    for (CartPromotionItem cartPromotionItem : cartPromotionItemList) {
        PmsSkuStock skuStock = skuStockMapper.selectByPrimaryKey(cartPromotionItem.getProductSkuId());
        skuStock.setLockStock(skuStock.getLockStock() + cartPromotionItem.getQuantity());
        skuStockMapper.updateByPrimaryKeySelective(skuStock);
    }
}
```

**这是典型的 read-modify-write，并发下会丢失更新。**

## 四、★★ 重点：`lockStock` 的并发缺陷分析

### 三段式库存的生命周期

| 阶段 | 方法 | 位置 | 手法 |
|---|---|---|---|
| **下单** | `lockStock` | impl **734-740** | Java 内存 read-modify-write |
| **支付** | `updateSkuStock` | `PortalOrderDao.xml` **50-67** | SQL 原子 `stock - ?` |
| **取消/超时** | `releaseSkuStockLock` | `PortalOrderDao.xml` **77-93** | SQL 原子 `lock_stock - ?` |

### 缺陷 1：丢失更新（lost update）

时序（两个并发下单请求，同一 SKU，各买 1 件，初始 `lock_stock = 0`）：

```
T1: SELECT lock_stock → 读到 0
T2: SELECT lock_stock → 读到 0          ← 都读到旧值
T1: 内存计算 0 + 1 = 1
T2: 内存计算 0 + 1 = 1                  ← 各自在 Java 里加
T1: UPDATE lock_stock = 1      ✅
T2: UPDATE lock_stock = 1      ← 覆盖了 T1 的结果
```

**结果：`lock_stock = 1`，但实际锁定了 2 件 → 少锁了一件 → 有超卖风险。**

关键点：这里用的是普通 `selectByPrimaryKey`（**不是 `SELECT ... FOR UPDATE`**），所以读不参与行锁。行锁只在 UPDATE 时才加，而此时两个事务的内存计算已经各自完成了。

### 缺陷 2：TOCTOU（检查与使用之间存在时间窗）

`generateOrder` 里的顺序是：

```java
if (!hasStock(cartPromotionItemList)) {    // 第 124 行：先检查
    Asserts.fail("库存不足，无法下单");
}
...
// 中间隔了 40 行：优惠券计算、积分分摊、实付金额计算……
lockStock(cartPromotionItemList);          // 第 165 行：后使用
```

检查和使用之间隔了 40 行代码的执行时间。并发下**检查时够、锁定时不够**。

### 缺陷 3：没有 affected rows 校验

`lockStock` 不检查 UPDATE 是否真的影响了一行，失败静默通过。

### ★ 最有力的证据：同一个项目里有正确写法

`PortalOrderDao.xml` 的支付扣减（第 50-67 行）：

```xml
<update id="updateSkuStock">
    UPDATE pms_sku_stock
    SET
        stock = CASE id
        <foreach collection="itemList" item="item">
          WHEN #{item.productSkuId} THEN stock - #{item.productQuantity}
        </foreach>
        END,
        lock_stock = CASE id
        ...
```

**对比很清楚**：`SET stock = stock - #{qty}` 是**数据库内原子运算**（InnoDB 行锁保证），而 `lockStock` 是**先查出来、在 Java 里加、再写回整个对象**。

> 同一个项目、同一个业务域，支付和释放都用了原子 SQL，**唯独下单锁定用了 read-modify-write**。这不像刻意设计，更像遗漏。
>
> 面试时可以这样表述：**"我在复健时发现项目里支付和释放库存都用 SQL 原子运算，只有下单锁定是先查后写，我怀疑是不一致实现，做了并发验证后确认存在丢更新。"** ——这比"mall 有 bug"的说法专业得多，而且证明你能看出代码风格的不一致。

### 改造方案

**方案 A（推荐）：SQL 原子 + 条件校验，一步解决缺陷 1 和 2**

```xml
<update id="lockSkuStock">
    UPDATE pms_sku_stock
    SET lock_stock = lock_stock + #{quantity}
    WHERE id = #{skuId}
      AND stock - lock_stock >= #{quantity}
</update>
```

Java 侧：

```java
int affected = skuStockMapper.lockSkuStock(skuId, quantity);
if (affected == 0) {
    Asserts.fail("库存不足：" + skuId);   // 事务回滚
}
```

**为什么这样就好了**：
- `lock_stock + ?` 在数据库内完成 → 不存在丢更新
- `WHERE stock - lock_stock >= ?` 把校验和更新合并成原子操作 → 不存在 TOCTOU
- `affected == 0` 就是"库存不足"的信号 → 缺陷 3 也解决了

**方案 B（了解即可）：乐观锁**

给 `pms_sku_stock` 加 `version` 字段，`updateByPrimaryKeySelective` 带版本条件，失败重试。适合冲突率低的场景；秒杀这种高冲突场景反而会大量重试。

### 一个值得讨论的取舍（面试加分）

改造后是"一条 SQL 一个 SKU"，下单 3 个商品就是 3 次往返。批量 SQL（`CASE WHEN`）能减少往返，但**批量 UPDATE 的 affected rows 是总数，无法区分是哪个 SKU 不够**，就失去了精确定位能力。

> **取舍**：串行单条（能精确报错、往返多）vs 批量（快、但只能整体回滚）。在 mall 的规模下选串行单条更合适——一次下单商品数通常个位数，而报错定位的体验更重要。

### 验证方法

用 JMeter / ab 对同一 SKU 并发下单（比如 50 并发各买 1 件），改造前后对比：

```sql
-- 实际锁定数量应等于成功下单的总件数
SELECT lock_stock FROM pms_sku_stock WHERE id = ?;
```

改造前 `lock_stock` 会小于成功下单总数（丢更新），改造后严格相等。

**这就是简历上那个"数字"的来源。**

### ⚠️ 一个必须纠正的判断

我一开始搜索 `OmsPortalOrderServiceImpl` 的实现类，**没找到 `@Transactional`，差点得出"下单流程没有事务"的错误结论**。

实际上事务是有的 —— 但**注解写在接口上**：

```
mall-portal\src\main\java\com\macro\mall\portal\service\OmsPortalOrderService.java:26
```

```java
/**
 * 根据提交信息生成订单
 */
@Transactional                                    // ← 第 26 行，在接口里
Map<String, Object> generateOrder(OrderParam orderParam);
```

**这个坑值得记住**：找 `@Transactional` 要同时搜接口和实现类。

顺带说一句：Spring 官方文档明确建议 **`@Transactional` 加在具体类（实现类）上，而不是接口上**。mall 的写法虽然通常能生效，但不是推荐做法 —— 这也可以是一个改造点（把注解从接口移到实现类），不过属于规范性问题，不像 `lockStock` 那样有真实缺陷。
